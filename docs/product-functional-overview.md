# DBAgent 总体功能设计

## 1. 产品目标

DBAgent 是面向开发者、数据库管理员和企业数据团队的 AI 数据库治理与运维平台。

产品通过 SDK、API、CLI 和轻量 WebUI 提供能力，核心覆盖三个大模块：

1. AI SQL 生成与执行。
2. AI 数据库治理与运维。
3. Agent、MCP、Skills 与安全行动。

DBAgent 支持从单个数据库实例扩展到数据库集群、数据库群和复杂数仓。系统采用“确定性程序持续运行，AI 处理关键问题，工作人员设置授权边界并负责高风险决策”的方式控制成本与风险。

## 2. 总体原则

- AI 是认知和决策中枢，不负责持续采集每一项指标。
- 数据采集、固定规则、权限判断和安全拦截优先使用确定性程序。
- AI 只在用户请求、重要事件、复杂诊断和周期性综合评估时介入。
- 所有结论必须区分数据库事实、规则判断和 AI 推断。
- 所有外部动作都必须经过统一权限、安全策略和审计。
- MCP 提供外部能力，Skills 提供处理流程，但都不能扩大用户权限。
- 单数据库是最小接入单元，统一资源模型支持向集群和数仓扩展。

三个大模块不是三套独立系统，其依赖关系是：

```text
公共基础能力
→ 大模块三：Agent、扩展与安全运行层
→ 大模块一：AI SQL / 大模块二：治理与运维
```

## 3. 公共基础能力

### 基础能力 1：大模型能力

**子模块设计**

- 接入国内外云模型、OpenAI-compatible 模型和私有化模型。
- 支持对话、推理、Embedding、Reranker、结构化输出和 Tool Calling。
- 按任务准确率、延迟、成本和隐私要求选择模型。
- 提供超时、重试、降级、缓存和 Token 预算。

**子模块达到的效果**

- 上层功能不依赖某一家模型厂商。
- 简单任务使用低成本模型，复杂任务按需使用高能力模型。
- 模型失败不会使监控、规则检查和安全控制停止工作。
- 每次调用都可以追踪模型、版本、延迟、Token 和成本。

### 基础能力 2：数据库接入与能力描述

**子模块设计**

- 通过 `pg`、JDBC 等 Driver 接入数据库和数仓。
- 每种数据源声明方言、事务、EXPLAIN、异步查询、取消、权限和治理运维能力。
- 提供统一的元数据读取、状态采集、SQL 执行和运维动作接口。

**子模块达到的效果**

- 上层功能使用统一能力，不直接依赖某个 Driver。
- 新数据库可以逐步接入，不需要重写 AI SQL 和 Agent 主流程。
- 数据源不支持某项能力时，系统明确提示，不伪装成功。

### 基础能力 3：统一资源与状态模型

**子模块设计**

统一描述以下资源：

```text
组织 → 项目 → 环境 → 数据平台 → 集群 → 实例
     → 数据库 → Schema → 表/视图 → 字段 → SQL/任务/数据管道
```

资源同时保存结构、关系、配置、权限、运行状态、历史变化和能力信息。

**子模块达到的效果**

- 单实例、集群、数据库群和数仓使用同一套管理模型。
- 治理规则、权限和任务可以按层级继承。
- Agent 只获取当前问题相关的资源和关系，避免上下文无限扩大。

### 基础能力 4：公共类型与合同

**子模块设计**

- 统一定义连接、资源、查询、风险、批准、执行、取消、任务、历史和使用量等公共类型。
- 统一 SDK、API、CLI、WebUI 与内部模块之间的请求、响应、状态和错误语义。
- 公共合同只描述对外行为，不暴露具体 Driver、模型或存储实现。
- 本子模块只负责类型、合同与兼容性；任务运行、批准和执行行为归大模块三负责。
- 合同变更需要版本、兼容性检查和明确的迁移方式。

**子模块达到的效果**

- 所有产品入口对同一状态和错误给出一致结果。
- 数据库 Driver、Agent、MCP 和 Skills 可以通过稳定合同协作。
- 新增数据库或产品入口时可以复用现有能力，不重复定义数据结构。
- 不兼容变更能够在发布前被测试发现。

### 公共基础达到的效果和性能

| 维度 | 目标 |
|---|---:|
| 模型、Driver 和数据源能力可识别率 | 100% |
| 不受支持能力的明确失败率 | 100% |
| Secret 进入模型上下文或普通日志 | 0 |
| 公共资源状态来源可追溯率 | 100% |
| 公共能力异常影响确定性监控与安全控制 | 0 |
| 公共合同兼容性测试通过率 | 100% |
| 未声明版本或迁移方式的破坏性变更 | 0 |

# 大模块一：AI SQL 生成与执行

## 目的

将用户自然语言转换为符合数据库结构、业务知识和安全策略的 SQL，并完成验证、批准、执行、结果解释和反馈闭环。

## 1.1 自然语言理解

**子模块设计**

- 识别查询、写入、结构变更和管理操作意图。
- 提取业务实体、指标、时间、范围、排序和聚合条件。
- 支持多轮上下文、指代消解和条件追加。
- 当业务含义不明确时主动追问。

**子模块达到的效果**

- 系统理解的是用户目标，而不是机械翻译句子。
- 对“最近”“最好”“活跃用户”等模糊概念先确认业务定义。
- 用户可以通过自然语言继续筛选、排序和修改查询。

## 1.2 数据库知识与 RAG

**子模块设计**

- 构建包含 Schema、表关系、业务术语、指标、规则、文档和已验证 SQL 的知识库。
- 组合关键词、向量、关系图、规则和 Reranker 检索。
- 对检索结果执行权限过滤、冲突检查、版本检查和上下文裁剪。
- Schema 变化后增量更新相关知识。

**子模块达到的效果**

- 大型数据库中仍能准确找到相关表、字段、关系和业务定义。
- 每条关键知识都有来源，用户可以理解 SQL 的生成依据。
- 失效字段、冲突知识和无关 Schema 不会直接进入生成上下文。

## 1.3 SQL 规划与生成

**子模块设计**

- 先生成查询计划，再生成对应数据库方言的 SQL。
- 支持关联、聚合、子查询、CTE、窗口函数和业务指标。
- 必要时生成多个候选 SQL 并进行排序。
- 输出 SQL、查询计划、使用的知识、风险等级和置信度。

**子模块达到的效果**

- SQL 结构与用户问题和数据库能力保持一致。
- 用户能够看到系统准备查询什么、为什么这样查询。
- 更换数据库引擎时复用相同主流程，仅替换对应能力适配。

## 1.4 SQL 验证与修正

**子模块设计**

- 验证语法、方言、Schema、字段类型、表关系和业务规则。
- 使用 AST、EXPLAIN、成本估计和受控 Dry Run 检查性能与风险。
- 验证失败后根据错误原因修正，默认最多自动修正两轮。
- 对写操作补充影响范围、可回滚性和执行前状态检查。

**子模块达到的效果**

- 不存在的表、字段和明显错误 SQL 不进入执行阶段。
- “能够执行”与“符合业务意图”分别验证。
- 修正失败时向用户说明原因，不继续盲目尝试。

## 1.5 权限与批准模式

**子模块设计**

- 对 SQL 识别读、写、DDL、权限和管理操作，并评估对象、环境与影响范围。
- 调用大模块三提供的统一批准模式和安全策略，不在 AI SQL 内重复实现权限系统。
- 读操作默认允许，但仍检查副作用函数、锁、敏感数据、查询成本、超时和结果规模。

**子模块达到的效果**

- 用户清楚当前 SQL 的风险、授权范围和是否需要确认。
- SQL 特有风险能够进入统一审批和安全执行流程。
- AI SQL 不能绕过数据库账号权限和系统安全底线。

## 1.6 SQL 执行与结果

**子模块设计**

- 通过大模块三的安全执行能力运行 SQL，并补充只读事务、超时、行数限制、结果大小限制、流式返回和取消等 SQL 专用控制。
- 写操作执行前展示影响和批准状态，执行后检查影响行数与数据库状态。
- 返回结构化结果、SQL 解释、数据摘要和后续追问建议。
- 明确区分数据库结果和 AI 解释。

**子模块达到的效果**

- 用户能够安全获得结果，并随时知道任务处于哪个阶段。
- 查询失败时说明是否真正执行、数据库是否发生变化以及下一步建议。
- 网络重试不会造成重复写入。

## 1.7 反馈、评测与审计

**子模块设计**

- 收集用户对 SQL、业务术语、表关系和结果的反馈。
- 用户修正内容经过验证后才能进入知识库。
- 通过统一审计能力记录问题、知识来源、模型、SQL、验证、批准、执行和结果摘要。
- 使用结果等价率而不是仅用 SQL 字符串一致率评测准确性。

**子模块达到的效果**

- 系统可以持续提升准确率，同时避免错误反馈污染知识库。
- 每次 SQL 生成与执行都可以复查和重放。
- 可以比较不同模型、Prompt、知识版本和策略的效果。

## 大模块达到的效果和性能

初始目标如下，后续通过真实评测集校准：

| 维度 | 目标 |
|---|---:|
| 相关表召回率 | ≥ 98% |
| 相关字段召回率 | ≥ 95% |
| 简单查询首次结果正确率 | ≥ 95% |
| 追问或修正后的整体成功率 | ≥ 90% |
| 未批准写操作 | 0 |
| 关键知识来源可追溯率 | 100% |
| RAG 上下文精确率 | ≥ 85% |
| RAG 检索 P95 | ≤ 500ms |
| 简单查询生成与验证 P95 | ≤ 8 秒，不含数据库执行 |
| 首个处理状态展示 | ≤ 500ms |
| 简单任务输入 Token | 目标 ≤ 4,000 |
| 中等任务输入 Token | 目标 ≤ 8,000 |
| 复杂任务输入 Token | 默认预算 ≤ 16,000 |

### 场景示例

用户询问“最近三十天复购金额最高的十个客户”。系统检索“复购”和“客户金额”的业务定义，找到订单、客户与退款关系，生成并验证 SQL，展示使用的指标和表，用户确认后执行并返回结果。

用户要求“把异常订单改为待审核”。系统识别为写操作，计算影响行数并展示风险。严格模式下必须逐次批准；自治模式下也只能在预先授权的订单范围内执行。

# 大模块二：AI 数据库治理与运维

## 目的

持续理解数据库和数仓的结构、配置、权限与运行状态，主动发现问题，生成有证据的治理或运维建议，并在工作人员决策后完成处理和复查。

## 2.1 状态采集与分层汇总

**子模块设计**

- 通过 Driver 持续采集结构、配置、会话、事务、锁、SQL、索引、容量、复制、备份和权限信息。
- 通过 MCP 接入监控、日志、云平台、调度、数据目录和工单系统。
- 在实例、集群、项目和平台层逐级汇总，只保留变化、异常和关键关系。
- 常规采集、阈值判断和固定规则不调用大模型。

**子模块达到的效果**

- 即使 AI 暂时不可用，监控、巡检和告警仍然工作。
- 数据库数量增加不会导致 AI 调用量按固定周期线性增长。
- 每项运行事实都包含来源、采集时间和有效期。

## 2.2 AI 数据库运维

**子模块设计**

- 诊断慢查询、执行计划、锁、长事务、连接、索引和统计信息。
- 分析容量、资源、配置、复制、高可用、备份和恢复状态。
- 关联指标、日志、SQL、配置和最近变更，形成故障时间线。
- 输出根因候选、证据、影响、临时止损和长期方案。

**子模块达到的效果**

- 用户可以直接询问“数据库现在有什么问题”。
- 系统能够主动发现关键异常，而不是只等待用户提问。
- 诊断明确区分已确认事实、AI 推断和处理建议。

## 2.3 AI 数据库治理

**子模块设计**

- 治理资产、元数据、命名、结构、数据质量和生命周期。
- 识别敏感数据、过度授权、公共账号和权限继承风险。
- 分析冗余对象、Schema 变化、数据血缘和下游影响。
- 支持组织、项目和环境级治理规则、例外与评分。

**子模块达到的效果**

- 每个治理问题包含对象、规则、证据、风险等级和建议。
- 同一规则可以应用于一个实例，也可以继承到整个数据库群。
- 整改完成后自动复查，确认问题真正解决。

## 2.4 AI 动态分析策略

**子模块设计**

系统根据状态进入不同策略：

- 稳定状态：确定性采集，AI 低频综合评估。
- 关注状态：提高相关采集频率，AI 做初步分析。
- 事件状态：收集关键上下文，AI 深入诊断并生成方案。
- 处理后状态：加强复查，稳定后恢复普通周期。

AI 可以建议调整采集周期、告警阈值和治理规则，但重要调整需要工作人员批准。周期评估到期本身属于有效触发；命中缓存且没有产生模型调用，不计为重复 AI 分析。

**子模块达到的效果**

- AI 只在值得分析时工作，避免持续消耗 Token。
- 重要事件获得更多分析资源，稳定资源保持低成本运行。
- 策略调整有原因、范围、有效期、版本和恢复方式。

## 2.5 问题、事件与任务闭环

**子模块设计**

- 将发现统一转化为问题或事件，记录对象、证据、等级、影响和负责人。
- 将处理建议转化为可审批、可执行、可取消和可复查的任务。
- 支持观察、忽略、深入分析、人工修改、批准执行和转交。
- 处理完成后记录结果，并沉淀为知识或 Skill。

**子模块达到的效果**

- 治理运维不是一次性对话，而是可跟踪的工作闭环。
- 工作人员拥有策略制定、授权收回和高风险最终决策权；系统可以在已批准范围内自动处理低风险任务。
- 处理经验可以被复用，同时保留人工验证和版本控制。

## 2.6 从单实例到复杂数仓

**子模块设计**

- 单实例重点管理 SQL、锁、事务、索引、配置和权限。
- 集群增加拓扑、复制、高可用和故障转移。
- 数据库群增加统一巡检、风险排名、容量和批量治理。
- 数仓增加任务、血缘、数据新鲜度、指标一致性、计算成本和业务影响。
- 数仓外部系统通过 MCP 接入统一资源、事件和任务模型。

**子模块达到的效果**

- 小型用户不需要部署复杂平台即可获得核心能力。
- 大型用户可以扩展采集、MCP 和执行节点，而不改变治理模型。
- 单数据库问题可以关联到数仓任务和下游业务影响。

## 大模块达到的效果和性能

| 维度 | 目标 |
|---|---:|
| 常规采集与固定规则 Token 消耗 | 0 |
| 未到周期评估时间且状态无变化时的重复 AI 调用 | 0 |
| 事实来源与时间标记覆盖率 | 100% |
| 治理运维问题证据覆盖率 | 100% |
| 规则在数据到达后的判断 P95 | ≤ 10 秒 |
| 标准事件首份 AI 建议 P95 | ≤ 60 秒，不含外部系统延迟 |
| 处理任务复查覆盖率 | 100% |
| 未批准高风险动作 | 0 |
| 诊断、批准和执行审计覆盖率 | 100% |

Token 按数据库每日、每次事件和每次治理评估设置预算。相同状态复用已有分析，简单分类优先使用低成本模型。

### 场景示例

单个 PostgreSQL 出现响应变慢。规则系统发现等待事件异常后触发 AI，Agent 获取慢 SQL、锁链、执行计划和最近配置变化，生成带证据的根因分析。工作人员批准优化方案后执行，并持续观察指标是否恢复。

企业数仓的上游字段被删除。DBAgent 通过 MCP 获取调度任务、数据目录和下游指标关系，识别受影响任务和报表，创建治理任务并通知负责人，在变更完成后重新验证血缘和数据新鲜度。

# 大模块三（公共运行层）：Agent、MCP、Skills 与安全行动

## 目的

让 Agent 在统一权限和审计边界内组合内置能力、用户 MCP Server 和 Skills，完成跨数据库、监控、云平台和企业系统的复杂任务。

## 3.1 Agent 决策中枢

**子模块设计**

- 接收用户请求、告警事件、定时任务和治理问题。
- 选择知识、Skill 和 Tool，形成任务步骤并持续检查结果。
- 支持暂停、恢复、取消、人工介入和任务状态查询。
- 控制上下文、模型、轮次、Token 和执行时间预算。

**子模块达到的效果**

- Agent 只处理需要理解、关联和决策的问题。
- 确定性任务不依赖模型，复杂任务能够分步骤完成。
- 模型失败、预算耗尽或证据不足时安全停止并说明原因。

## 3.2 Tool 系统

**子模块设计**

- 将数据库、监控、治理和外部系统能力统一描述为 Tool。
- 每个 Tool 声明输入输出、作用对象、权限、风险、超时和验证方式。
- 不向 Agent 暴露不受控的万能数据库执行接口。

**子模块达到的效果**

- Agent 调用的是边界明确的能力，而不是直接使用 `pg` 或 JDBC。
- 内置 Tool 和 MCP Tool 使用相同的权限、安全和审计流程。
- Tool 失败不会被错误解释为任务成功。

## 3.3 MCP 接入与对外服务

**子模块设计**

- 作为 MCP Client 接入用户自己的 MCP Server。
- 发现并适配 Tools、Resources 和 Prompts。
- 管理认证、权限映射、健康状态、超时、隔离和生命周期。
- 提供官方 DBAgent MCP Server，将查询、治理和运维能力提供给其他 AI 客户端。

**子模块达到的效果**

- 用户可以接入监控、日志、云平台、CMDB、工单和内部系统。
- 单个 MCP Server 故障不会影响核心数据库能力。
- 外部 Tool 不能绕过 DBAgent 的权限和批准策略。

## 3.4 Skills 系统

**子模块设计**

- 支持用户导入、创建、测试、启用和更新 Skills。
- Skill 描述触发条件、处理步骤、Tool 依赖、风险停止点和结果要求。
- 支持个人、项目和组织范围，以及版本、来源和可信等级。
- 脚本型 Skill 只有在具备安全沙箱后才能执行。

**子模块达到的效果**

- 企业可以把巡检规范、治理规则和故障 Runbook 交给 Agent 使用。
- Skill 可以组合能力，但不能自行授予权限。
- Skill 更新可以评测、回滚和审计。

## 3.5 安全策略与行动执行

**子模块设计**

- 提供严格、平衡和自治三种策略预设：严格模式逐次批准写入及管理动作；平衡模式允许策略内低风险动作自动执行；自治模式只在预授权范围内自动行动。
- 对所有动作执行权限检查、风险分类、影响分析和批准判断。
- 支持前置检查、Dry Run、分批执行、并发限制、事务、幂等和回滚。
- 执行后验证预期效果，异常时停止后续步骤并通知工作人员。
- 设置不可被自治模式覆盖的硬性禁止规则。
- 生产环境不可回滚的高风险动作、权限提升和安全策略变更始终需要逐次批准。

**子模块达到的效果**

- 同一安全边界保护 AI SQL、治理、运维、MCP 和 Skills。
- 高风险动作始终可见、可控、可停止和可追溯。
- 网络重试、Agent 重试和任务恢复不会导致重复操作。

## 3.6 产品入口

**子模块设计**

- SDK：嵌入用户自己的服务和产品。
- API：向不同语言和企业系统提供统一服务。
- CLI：配置、测试、启动服务和执行常用任务。
- WebUI：管理连接、模型、知识、MCP、Skills、任务、批准和审计。

WebUI 只承担配置、任务、批准、审计和状态管理。

**子模块达到的效果**

- 所有入口共享同一 Runtime、权限和任务状态。
- 用户可以先通过 CLI/WebUI 试用，再通过 SDK/API 集成。
- 不需要复杂前端也能管理完整核心能力。

### 场景示例

用户接入自己的 Prometheus MCP Server，并导入“生产数据库每日巡检”Skill。Skill 通过监控 Tool 和数据库 Tool 收集信息，规则系统先筛选异常，Agent 只分析关键问题，最后生成巡检任务和建议。

Agent 建议终止阻塞会话。Tool 首先返回阻塞关系和影响范围，安全策略根据生产环境要求工作人员批准。批准后执行，随后重新检查锁链；如果问题没有解决，任务保持未完成并请求人工介入。

## 4. 指标验收口径

- “相关表、字段和知识”以人工标注的评测集为准，同时计算召回率与上下文精确率。
- “首次结果正确”指第一个 SQL 的执行结果与标准结果等价；“整体成功”覆盖全部难度，并允许一次追问和最多两轮修正。
- 简单查询为单表、过滤和基础聚合；中等查询包含多表关联、分组或常见业务指标；复杂查询包含多层 CTE、窗口函数或跨业务域规则。
- “标准事件”来自固定故障与治理场景集，计时从所需证据到达开始，到生成可供决策的首份建议结束。
- P95 指标至少使用完整固定评测集或不少于 1,000 次有效样本，并分别标记模型、网络、外部系统和数据库执行耗时。
- “单个 MCP 故障影响核心服务为 0”指内置数据库能力继续可用，依赖该 MCP 的任务明确降级或失败。
- 百分比指标以固定评测集或指定观察周期内全部适用事件为分母；100% 表示没有遗漏记录、未验证任务或未追溯调用。
- 标记为 0 的零容忍指标必须通过全部权限绕过、危险操作、Secret 泄露、重复执行和故障注入用例，并在指定生产观察周期内保持零事件；任一事件都视为发布阻断或最高级故障。
- 所有指标都必须记录模型、Prompt、知识版本、数据源规模和测试环境，确保结果可以复现。

## 5. 总体用户效果

完成上述功能后，用户应获得以下体验：

- 用自然语言安全查询和操作数据库。
- 在单实例上快速获得 AI DBA 能力。
- 在数据库群和数仓中统一查看资产、风险、事件和任务。

- 工作人员制定授权边界并处理高风险决策，系统在批准范围内自动完成低风险任务。
- 用户可以接入自己的 MCP Server 和 Skills，而不破坏统一安全边界。
