# 自适应循环、任务计划与完成验证

## 1. 目的

让 Agent 根据新证据自主选择检索、SQL、文件、网络、MCP 或子 Agent，并在真正满足用户目标后结束。

## 2. 单一循环

```text
理解目标
→ 判断是否需要计划
→ 创建或更新任务
→ 发现并加载相关能力
→ 探索和执行
→ Runtime 记录真实工具结果与完成证据
→ Verify：验证最后一次相关执行、产物与交付状态
→ Finalize：形成真正面向用户的终态答复
→ 完成 / 换路 / 请求用户补充
```

简单问答可以在一轮内结束。多步骤、包含副作用、需要多个数据源或产物的任务必须建立计划。Plan 是结构化工作状态，不是另一种 Agent 策略。

## 3. 任务状态

每个任务包含：

- 目标与可读标题。
- `pending / in_progress / completed / cancelled` 状态。
- 可选的简短说明。
- 最近更新时间。

每次只允许一个任务处于 `in_progress`。压缩和恢复后任务状态不丢失。

Plan 由模型维护，用于组织工作和向用户显示进度，不承担事实证明。Runtime 从实际 SQL 执行、文件写入、批准和用户输入中产生独立证据；模型不能提交证据 ID，也不能仅凭把计划改成 `completed` 绕过完成验证。一次用户请求结束后清除当前 Plan。

## 4. 自主探索与无进展换路

- 工具调用关联当前任务和预期获得的信息。
- 对工具名、规范参数和目标资源生成内部动作签名，避免在资源未变化时重复调用。
- 每轮计算是否得到新事实、状态变化、结果或产物。
- 无新证据时，不向用户返回抽象的 `incomplete` 或 `blocked`；运行时要求 Agent 更换工具、查询方式、Skill 或子 Agent。
- 缺少外部信息且无法继续时，最终说明具体原因和用户需要补充的内容。
- 最大迭代、超时和失败次数只是内部熔断，不是正常工作策略。
- 不以固定 SQL 次数触发检查点。模型根据目标和观察自主探索；Runtime 只在重复动作、无信息增量、失败恢复或物理上下文窗口临界时介入收敛。
- Provider 把 Tool Call 退化为 `<tool_call>`、DSML 等文本时，不得当成最终回答；Runtime 会请求使用标准 Tool Calling 重试，仍不兼容时给出明确原因。

## 5. 完成验证

模型停止调用工具不等于任务完成。结束前验证：

- SQL 生成任务已经通过语法解析。
- SQL 执行任务已有数据库成功结果。
- 写入任务已有影响行数、返回值或结构刷新证据。
- 文件任务的目标文件确实存在。
- 用户请求的数据回答由数据库返回的必要结果支持。
- Runtime 使用当前 Run 中真实工具结果验证数据库、Tool 和产物证据，不接受模型声明的证据。
- 最终答复声称成功时，最后一次承担交付的 SQL 必须成功；更早的成功结果不能掩盖最后一次失败。
- 最终答复不能仍是“让我继续检查/验证”等过程语句；查询行由独立结果载荷交付，答复只需说明终态和必要摘要。

被用户拒绝、数据库只读、取消或超时也可以成为真实终态，但最终答复必须明确交付“未执行/失败/拒绝/超时”等结果；“已完成”之类与工具状态矛盾的文本不能通过。可恢复的语法或对象错误仍应优先修正。

验证流程采用“模型提出完成、Runtime 确定性验证”的分工。验证失败时继续循环；Finalize 首次仍输出过程语句时会得到一次明确纠正。若数据库结果已经独立交付但模型仍未形成终态文本，运行时使用确定性的最小交付说明；没有交付证据时不能标记完成。所有合理路径耗尽时给出可行动的说明。

## 6. 工程与验收

工程入口：

- 自适应循环：`packages/core-agent/src/react-agent.ts`
- 完成验证：`packages/core-agent/src/completion-verifier.ts`
- 任务计划：`packages/core-agent/src/task-plan.ts`
- 工具失败分类：`packages/core-agent/src/tool-failure-classifier.ts`
- Checkpoint：`packages/core-agent/src/checkpoint-store.ts`

验收覆盖简单快速路径、复杂计划、恢复、用户转向、重复动作、错误修正、权限拒绝后的替代路径、真实工具证据和完成门禁。
